# Construction Intelligence — Permit Collection Operating Standard
Version 1.0 · proposed implementation standard · 27 November 2026 (Mountain Time)
Owner: collector/platform development; consumer: Scout (read-only sales intelligence). Applies to new city/county/state permit collectors and repairs; public procurement uses a separate event schema. This is a design standard, not a claim that new coverage is live.

## 1. Objective and operating boundaries
Collect trustworthy, actionable private construction events before or during the material buying window, with traceable issuer IDs, verified stage/date, source-reported construction companies, project scale and direct evidence. Prioritize all Idaho, Eastern Washington, Eastern Oregon and Jackson Hole/Teton Valley, based on the six partner networks: 84 Lumber, Builders FirstSource, Capital Lumber, Boise Cascade, Franklin Building Supply and Sunpro. Confirm actual service areas and partner roles; proximity is not proof of supply, stocking or purchasing authority. Preserve all existing out-of-territory data and deployments. Utah, Colorado, North Carolina and Kansas/Missouri are reference systems first, not current expansion priorities.

Platform developer owns acquisition, repair, validation, deployment and monitoring; Scout owns interpreting verified data, account matching, sales-stage qualification, visit recommendations and Salesforce-ready notes. No Scout writes to collectors or source records. No new external communications, credentials, access/security changes, actual rollback, destructive changes or scoring/qualification changes without separate owner permission. Existing conditional release authorization applies only when the specified gates pass. No recurring schedule changes or new monitoring jobs are requested by this standard.

## 2. Build one issuer at a time
Use the coverage CSV as an initial research queue. A market, postal city, dealer territory and legal issuing authority are different things. For each city/county, establish an issuer ID and boundary, permit types, official website, actual permit authority (including delegated/state services), known portals/reports, terms and access limitations, expected report cadence, coverage limits, fields/labels, freshness threshold, stable record identifier and acceptable fallback. Register aliases without merging distinct issuing authorities. For statewide shared feeds, record the jurisdiction on each row and demonstrate issuer mapping. Never advertise a whole state as covered simply because one city has data.

### Source preference (evidence first, not platform preference)
1. Official machine-readable issued-permit API, CSV/XLSX, or authorized dataset with documented field semantics (Socrata, ArcGIS, official exports).
2. Official report directory with current dated weekly/monthly documents; prefer original spreadsheet, otherwise structured PDF. Discover document links from visible parent/index instead of guessing filenames or numeric IDs.
3. Official public guest search/export or case lookup with explicit issued-date filter, bounded pagination and record details. Use ordinary public browser controls where permitted; do not call private endpoints, solve challenges, rotate proxies, evade restrictions or access authenticated data without permission. Single case lookup is not proof of bulk completeness.
4. Authorized manual export plus validated offline import, with original document hash, report period, title, page order, scope and provenance. Report manual freshness explicitly, not as an automated collector.
5. Official planning/application evidence when issuance is unavailable. Keep separate early-stage event types. Aggregate announcements, parcel polygons, business directories and third-party leads may guide research but cannot establish permit-level issuance.

Check published access/reuse conditions and robots policy where applicable; stop on explicit restrictions (401/403/429/challenge or denial). An official public URL alone does not establish commercial reuse permission. If unavailable, document the approved export or permission needed; do not keep probing restricted routes. A failed transport is not a verified empty report.

### Source onboarding worksheet
Required fields: issuer_id, authority_name, state, county/city, market_id, scope (city/county/delegated, issue classes, valuation limits, historical window), source_id, official_landing_url, documented retrieval path, authorization/reuse note, access mode, update cadence and grace, required schema, ID field, authoritative issue/date fields, contractor role field, completeness control, fallback and latest evidence date, owner, current lifecycle state, next action and release reference. Store the worksheet in version-controlled source registry; keep sensitive credentials out of repository and logs.

## 3. Acquisition and resilience
Use a common adapter interface: discover → acquire → validate → normalize → reconcile → report. Share transport and validation libraries; keep issuer-specific mappings small and testable. Existing proven reference implementations: Seattle Socrata, Aurora ArcGIS, Eugene official Excel export, Meridian/Kootenai PDF reports, Nampa official Civic Access guest search, Utah planning notices, Idaho Public Projects verified artifact pipeline.

- Network: explicit connect/read deadlines; suggested starting values 10/45 seconds per request, total budget 120 seconds for simple feeds and 180 seconds for PDF/browser acquisition, up to 300 seconds only by documented exception. Bound pages, detail visits, bytes, dates and retries. Retry at most twice on transient connection/5xx errors with backoff and jitter; honor Retry-After and do not retry access-denied or challenge responses. Avoid unnecessary re-downloads through ETag/Last-Modified/hash where supported. Respect source cadence and request limits.
- ArcGIS/Socrata: validate service identity, schema, authoritative date fields, field aliases and types before fetching; verify query errors, pagination/caps, ordering and completion; deterministic ID tie-breaker; use counts or distinct ID lists when available. A successful HTTP response can still carry an API error or login shell. Never assume a recently updated GIS feature is newly issued.
- Reports: discover titles and URLs from official index, choose recent completed periods (at least two during onboarding), record original PDF magic/hash, pages and explicit period. Parse table geometry/headers; maintain multiline row boundaries and horizontal page pairing. Reconcile printed totals or record count controls; missing count is unverified, mismatch is partial. Check date belongs to the stated interval; reject shifted columns, conflicting IDs and ambiguous dates. A title or file modification date does not prove issuance.
- Portals: verify guest access, current visible labels, result counts, pages, scope and exact case links. Separate application and issuance, owner and contractor. Use browser only if needed and permitted; do not bypass login, CAPTCHA, terms or restrictions. Bound query windows; explicit zero may be valid only when full requested scope is verified.
- Failure isolation: each source runs with its own time budget and typed status; retain last verified history on error, stale or partial results. A new-source experiment or review queue cannot block unrelated validated publication (North Carolina lesson). Fail the release on broken integrity, not merely one upstream source outage. Log minimal structured diagnostics, no personal owner/contact detail or secrets.
- Runtime: pin compatible dependencies; confirm Chrome and PDF libraries on actual hosted runner. Prefer atomic commit of code plus workflow and fixtures to avoid transient broken intermediate branches. State workflows remain serial per target deployment; do not introduce extra schedules by default.

## 4. Record semantics and common contract
Keep the legacy data intact. Add a versioned normalized read model and explicit migration/reconciliation proposal; do not silently change old keys, scores, eligibility, first_seen or feed GUIDs. The accompanying JSON Schema is a proposed interchange contract for Scout and dashboard clients, not a replacement for current stores.

Identity: immutable internal record_id mapped to state + issuing authority + original permit/case number; preserve legacy source key and original number including leading zeros. Source observation has source_id, document/case URL, acquisition timestamp, raw field labels and file/hash or response reference, parser version. Same issuer/ID repeat observations append evidence or safely update permitted mutable fields with first_seen unchanged; conflicting evidence goes to review. Cross-issuer/address similarities create a possible-project-match group, not automatic deletion. Permit children/trade/parent records and phases remain distinct; units are not permit counts.

Dates/events: use explicit issued_date for actual issuance, application_date for received/submitted, planning_date or month for planning, status_date for lifecycle change, first_seen/last_seen for collector tracking. Event_date and event_date_kind carry the evidence type; never fill unknown issuance with first seen, report date, submission or a future hearing. Preserve date precision (day/month/unknown) and original status. Status/stage: planning, application, issued, construction-confirmed, completed/finaled, expired/canceled, unknown; distinguish source-reported current status from inference. An issued permit is not proof framing materials remain unpurchased or work has started. Future hearings and public procurement deadlines are not issued permits.

Classification: source permit type/work scope, normalized project type, existing policy qualification/score and policy version. Keep ground-up SFR, townhome/duplex, multifamily and eligible new commercial/industrial/hospitality per existing policies. Do not promote reroofs, trades, tenant improvements, pools, fences, accessory work or occupancy-only cases as new structural starts. Preserve all source observations as allowed, including nonqualifying and review-only rows; do not retroactively alter published membership without approval. Public works bidding/award/forecast records use a separate schema and dates.

Companies: preserve exact reported contractor/company text and role (GC, registered building contractor, builder, licensed professional, applicant, owner, unknown); use nullable normalized company_id and matching confidence only with evidence. Applicant, owner, contractor and buying decision-maker are not interchangeable. Do not publish unnecessary personal owner/contact names, home phone/email or raw private fields. Scout's named buyer, dealer path, product interest, project timing and next action are separate research overlays with evidence links/status, not authoritative permit facts.

Scale: valuation as reported, currency USD; null for unavailable and distinguish literal zero from missing/unknown. Units, living/floor area, lot/block/subdivision and project address only where source supports them. Do not infer sheet demand from valuation or living area alone. Keep source-reported scope, valuation, contractor and project link visible. Prefer case-specific actionable official URL; when only report link exists, label it report and include page/row reference; dataset URL remains separate.

## 5. Source health and publication manifest
Report separately: last_attempt_at, last_success_at (validated collection), latest_authoritative_issue_date, latest_other_event_date, event type/precision, report_period_end, data_age_days, expected_cadence, source availability (reachable, partial, restricted, unavailable, unknown), collection mode (automatic/manual/uncovered), outcome (success/partial/verified_empty/error/not_attempted), freshness (fresh/stale/unknown), coverage description, observed_count, qualifying_count, newly_added_unique_ids, retained_count, retained_latest_issue_date, duplicate/conflict counts, error class and next action. Counts from failure or incomparable scope are null, not zero. Track partial evidence without advancing comparable last-success checkpoint. Compare new IDs only to equivalent successful scope; distinguish newly observed old permits from recently issued ones.

Suggested initial freshness alerts: daily feed 3 days beyond expected update; weekly reports 14 days after period end; monthly 45 days after period end; adjust documented threshold for normal municipal posting lag, holidays and actual reporting schedule. Missing expected next report and old last issue are independent signals; no permits in a valid complete period is not stale by itself. Planning milestones use separate cadence. Store timestamps in UTC, display local jurisdiction date and America/Boise reporting time with explicit zone (Pacific for Washington/Oregon when relevant).

## 6. Standard dashboard and Scout export
Same layout across state permit sites (additive, no policy change):
A. Header: snapshot generated/published timestamps, coverage scope and freshness warning.
B. Summary: matching verified issued, applications, planning, unverified-date history; newly observed and recently issued separate; valuation with known-value coverage and counts. Display total stored/published separately from current filtered matches. Never call all retained records active leads.
C. Source cards: issuer, mode, observed vs retained, latest verified issue/event date, last validated pull, age, new unique IDs where comparable, health and coverage. Short diagnostics expandable; link official source and last release.
D. Filters: state/region/market, issuer, date basis, explicit date range or rolling preset (explicit range overrides preset), project/stage/type, lifecycle, contractor, evidence status, score, text search, new vs retained. Show active filters and counts; Show all/reset; explicit sort and stable tie-breaker. Pagination with no silent cap.
E. Default row order: evidence date newest first within selected stage, stable key tie-break; preserve existing default scoring/ranking until reviewed. Compact columns: Evidence date + kind | market / issuer | permit ID | project/address | stage/status | project type | reported contractor + role | units / sq ft / valuation | qualification/score | direct official record link | source report/dataset. On mobile, compact cards with expandable evidence; not horizontal page overflow. Unknown values displayed as “Not reported”; badges for meaningful states only.
F. Builder view: company name and exact role/evidence, recent verified issued counts by 30/90-day period, distinct permit IDs, known valuation and valuation coverage, market distribution, active/recently issued vs completed distinctions; preserve alias mapping with review. Do not assume a contractor is the buyer or aggregate duplicate phases as separate starts.
G. Exports: full matching sorted CSV independent of page size; formula injection protection, UTF-8, stable columns and date semantics. Versioned JSON + source manifest, per-issuer new-ID delta, and RSS GUIDs tied to stable IDs. Retain current feeds/links; distinct issued vs early-stage filters or feeds only after additive compatibility tests. The exact same filter must select the same IDs in UI and CSV/JSON.
H. Scout read-only view: standardized permitted records, source health, changes since previous successful snapshot, market/branch candidates, provenance, company role, stage, date age, scale, and direct links. Scout then adds researched project/builder, spec owner/purchaser/installer, supplier evidence, remaining buy window, potential ZIP/AdvanTech fit, next action, confidence and manual Salesforce-ready notes. Do not create product-fit, quantities, contacts, stocking or purchasing claims from permit alone.

Keep public project dashboard separate: procurement status, actual bid deadline vs forecast milestone, solicitation ID, agency, award/bidder roles, award value vs estimated/submitted bid, direct procurement link. Do not combine with permit counts.

## 7. Acceptance checklist and release
1. Verify official authority, approved access/reuse, current report cadence and schema. Save sample original bytes/hash (authorized storage) from at least two distinct actual periods or equivalent repeatable API samples; verify explicit issued dates and a representative row per class against the official source.
2. Fixture tests: normal, zero, error/timeout/403, schema drift, HTML instead of data, duplicate/conflict, partial/capped page, date out of period, missing role/value, misleading owner/applicant, trade/occupancy negative, year rollover, rolling window omission, repeated export. Test fixed regression fixtures independently of latest mutable production snapshot. Do not loosen tests to fit observed failures.
3. Integrate on isolated branch; run the actual entry point in hosted read-only CI against current main and real acquisition; replay into a temporary copy of ledger, then repeat. Compare exact prior keys, first_seen, raw evidence, existing qualification/score, published membership, builder totals and RSS GUID/order/content. Allow only explained new eligible records and deterministic cap effects. Test default views, filters, pagination, exact CSV membership and desktop/mobile browser. Record exact commit/tree, dependency versions, run IDs and outcome.
4. Before merge: current main and candidate tested together; no unrelated diff, no unexplained regression, no destructive changes, no source access violation; document pre-release artifact/history and safe rollback procedure (actual rollback requires owner approval). Separate research-only checks from production path. One release at a time.
5. Production: existing workflow or authorized trigger; verify collection, durable store, unique run/attempt artifact ID/name, bounded propagation retry, SHA-256 and required manifest/files, Pages deploy and actual served bytes vs verified artifact. A green build without live parity is not accepted. If a source fails, retain verified history and report failure; do not publish corrupt data. Stop on integrity/publication failure and diagnose.
6. After release: compare before/after new IDs, observed counts, latest verified issue date, retained rows, buyer/contractor fields, valuation, builder/RSS changes and real live assets. Verify next ordinary collection; source recovery and first release are distinct from sustained automation. Report narrow/partial scope honestly even when usable new data lands. Completion state = live verified + subsequent run verified. Do not call tests or a manually captured file “fixed”.
